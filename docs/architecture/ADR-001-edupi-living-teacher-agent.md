# ADR-001：EduPi 是教师工作的持续运行体

日期：2026-09-02  
状态：采用

## 决策

EduPi 不再按“聊天 + 一组教育模块”继续扩展。产品采用一个持续运行的教师工作闭环：

```text
教师自然输入 / 文件 / 图片 / 校历 / 课程表 / 学校通知
                     ↓
          感知 → 教育事实 → 注意与洞察
                     ↓
          提前规划 → 自动执行 → 候选产物
                     ↓
          教师确认 → 交付留痕 → 记忆与修正
                     ↺
```

Core 是这个闭环唯一的教育事实与状态所有者；Desktop 是它的可见身体、教师控制面和本地工具宿主。Desktop 不建立第二套学生、日程、任务、材料、记忆或执行状态。

产品北极星不是“老师使用了多少功能”，而是：

> 在老师想到这件事之前，EduPi 已经基于可信事实把可逆的教师内部工作准备好；老师主要做判断、修改与授权。

## 六层如何出现在 Desktop

六层不新增为六个抽象导航。它们分布在教师已经理解的工作域中，并通过同一条对象时间线贯通。

| Core 层 | Desktop 可见位置 | 教师看见的状态 |
| --- | --- | --- |
| 感知层 | AI 协作、任意页面拖入、日程、材料 | 已收到、正在识别、待核对、已成为事实 |
| 记忆层 | 教育记忆、班级学生抽屉、教学页 | 已记住、来源、版本、何时被使用、可手动修订 |
| 潜意识层 | 观察与洞察、今天、班级关注 | 酝酿中、证据增加、已浮出、已抑制 |
| 能力层 | 教学准备、任务详情、材料产物 | EduPi 正在调用哪类教育能力、输入与预期产物 |
| 调度层 | 日程、今天、工作区任务板 | 何时开始准备、正在做、阻塞、已提前完成 |
| 交付层 | 待我确认、材料、成长、通知收件箱 | 草稿、版本、审核、交付、结果与后续留痕 |

## 统一对象模型

Desktop 的日历项、任务卡、材料行、学生跟进和审核项不是五套互不相关的 UI。它们是同一 `work_case` 的不同投影。

```text
work_case
├── trigger       校历节点、课程、观察、通知、教师输入
├── facts         班级、学生、学科、日期、来源、置信度
├── plan          提前量、工作包、依赖、责任能力
├── executions    queued / running / draft_ready / failed / stale
├── artifacts     文件、摘要、版本、哈希、来源
├── decisions     接受、修改、暂缓、拒绝、回滚
├── delivery      内部使用或经授权外发的结果
└── learning      教师修改、结果反馈、下一轮策略候选
```

同一对象从日程、任务板、教学、班级或待我确认打开时，右侧详情必须展示同一身份、同一状态和同一时间线。

## 流动感的定义

流动感表达真实状态变化，不是粒子装饰：

- 新材料完成识别时，从“感知”进入“事实”的细线短暂流动；
- 工作进入执行时，任务卡与日历项显示同一个运行脉冲；
- 产物完成时，状态从“准备中”过渡到“待我确认”，并进入完成收件箱；
- 教师确认后，时间线出现回执，相关记忆显示一次“吸收”过渡；
- 来源变化时，旧产物明确变为 `stale`，流向新的准备版本；
- `prefers-reduced-motion` 下保留状态变化，不播放位移动画。

动画只由 Core receipt、execution revision 或 snapshot transition 驱动。没有真实状态变化时不播放。

## 自主性边界

- 可信日期和来源可以自动建立工作包。
- 教师内部分析、清单、教案框架、材料草稿可以自动执行并保存。
- 日期冲突、来源推断、学生高风险结论保持 `hold`，不猜测。
- 面向学生、家长、学校或公开渠道的内容最多自动准备到可发送草稿。
- 外发和不可逆桌面动作必须有明确授权与回执。
- 教师删除使用稳定 ID 软删除，来源事实保留；恢复必须是显式操作。

## 被拒绝的方向

- 为每个 Core 层增加一级导航：教师不应学习内部架构。
- Desktop 自己保存任务或动画状态：会制造第二事实源。
- 只做提醒：仍把实际工作留给老师。
- 用模型自述“已经完成”：完成必须对应产物、哈希、回执或真实状态。
- 全屏装饰动画：与教师工作无关，也无法解释系统正在做什么。

## 结果

后续需求优先被实现为可验证的纵向闭环，而不是新增孤立页面。每个闭环必须同时回答：触发来自哪里、Core 记住什么、何时自动开始、产物在哪里、教师如何修改、反馈如何改变下一轮，以及重启后是否仍然成立。
